# spec.md — 快照定时任务的运行日志（开始/结束 + 结束数据）

Status: implemented (2026-09-10)

来源：`.scratch/snapshot-task-run-logs/REQUIREMENTS.md`（2026-09-10 grilling 一轮 3 问全部拍板）。
决策记录：无新 ADR（实现细节落在 ADR-0021 快照生命周期与 worker 失败语义之内）。

## Problem Statement

两个内置快照任务（`stats_snapshot` / `stats_snapshot_rebuild`，均 `@every 1h`）在管理后台的任务日志里
几乎看不到内容，运维无法感知它们是否真的跑了、干了多少、花了多久：

- 生成任务：增量路径（绝大多数运行）一行日志都不打；首启/时区变更路径只有「开始全量回填」，
  没有完成行——长回填跑完没有任何收尾信号。
- 自愈任务：只在「补算 > 0」时打一行；无缺失（正常情况）时完全静默。
- 两者内部出错时只写一行日志，run 状态仍记 `success`——真失败在 run 列表上看不出来。

## Solution

1. 两个任务每次**实际执行**都留下开始/结束两行日志；结束行带本次数据：各粒度固化桶数 + 耗时，
   全量回填/时区重算场景额外带覆盖时间范围。
2. 空转运行（本次 0 个新闭桶 / 补算 0 个）照打结束行——「没干活」与「没跑」可区分。
3. 任务内错误交回 worker：run 列表显示「失败」并自动追加「任务执行失败：…」日志行。

## User Stories

1. 作为网关管理者，我希望 `stats_snapshot` 每次跑完都有「开始 / 完成」两行日志，以便确认任务真的执行了。
2. 作为网关管理者，我希望结束日志里看到本次固化的小时/天/月/年桶数，以便一眼知道这轮干了多少活。
3. 作为网关管理者，我希望没有新闭桶的空转运行也留下「桶数 0」的结束日志，以便区分「没干活」和「没跑」。
4. 作为网关管理者，我希望首启/时区变更的全量回填结束时看到固化桶数与覆盖时间范围，以便判断回填是否完整。
5. 作为网关管理者，我希望自愈任务无缺失时也看到「检查闭桶 N 个，补算 0 个」，以便确认扫描确实发生。
6. 作为网关管理者，我希望结束日志带耗时，以便察觉回填/自愈变慢。
7. 作为网关管理者，我希望任务真失败时 run 列表显示「失败」且日志里有失败原因，以便不必翻遍日志找错误。
8. 作为开发者，我希望「每次执行必有开始/结束日志（含空转）」由单测锁定，以便以后重构不把可观测性改回去。

## Implementation Decisions

1. **日志文本**（中文，数据内嵌在 message 里——`JobLogLayer` 只捕获 message 字段，结构化字段不会进 UI 日志）：

   | 场景 | 日志 |
   | --- | --- |
   | 生成·开始 | `统计快照生成开始` |
   | 生成·增量结束 | `统计快照生成完成：本次固化 小时桶 N 个 / 天桶 N 个 / 月桶 N 个 / 年桶 N 个，耗时 D` |
   | 生成·首启结束 | `统计快照全量回填完成：本次固化 …，覆盖 YYYY-MM-DD HH:MM ~ YYYY-MM-DD HH:MM，耗时 D` |
   | 生成·时区变更结束 | `统计快照时区变更重算完成：本次固化 …，覆盖 …，耗时 D` |
   | 自愈·开始 | `统计快照自愈开始` |
   | 自愈·结束 | `统计快照自愈完成：检查闭桶 N 个，补算 M 个，耗时 D` |
   | 自愈·未初始化 | 开始行之后接 `统计快照未初始化，本次跳过自愈（等待生成任务回填）` |

   - 原「统计快照自愈补算 {healed} 个缺失闭桶」一行由结束行取代（信息重复）。
   - 锁被占跳过（上次仍在运行）保持原 warn 单行，不算一次真实执行。
2. **数据收集**：`tasks.rs` 内一个运行统计结构（按粒度计桶数 + 最早起点/最晚终点），固化循环逐桶累加；
   不加写入行数、不加各级水位（用户否决）。生成/回填/自愈三条结束日志共用同一格式化函数。
3. **格式**：覆盖范围按设置表时区（`app_settings::timezone_sync`）格式化为 `YYYY-MM-DD HH:MM`；
   耗时用 `Duration` 的 Debug（`412.7ms` / `3.2s`）。无请求历史时回填 0 个桶、不带覆盖段。
4. **失败语义**（lib.rs 两个 handler）：handler 由 `stats_snapshot::jobs` 的两个工厂构造，
   错误 `?` 直交 worker（删除 handler 内自行 `tracing::error!` 后返回 `Ok(())` 的写法）；
   worker 既有 Err→`failed` 路径负责落状态与追加「任务执行失败：…」。被进程级锁跳过的运行
   返回 `Ok`（不算失败）。启动预热路径（不经过 handler）保持 `warn` 一行。
5. 前端零改动。

## Testing Decisions

- **缝**：`src/stats_snapshot/tasks.rs` 既有 `tests` 模块（与现有 6 个用例共用 `test_lock` 串行）。
  测试挂一个 `MakeWriter` 内存缓冲的 fmt subscriber（`set_default` 线程局部 → 用例跑默认
  current_thread runtime），断言日志消息文本。先例：`src/cron/log_capture.rs` 的捕获式测试。
- 用例 1（生成）：首启运行断言「开始」+「全量回填完成」+ 桶数 + 覆盖 + 耗时；紧接的无新闭桶运行
  断言「生成完成：本次固化」+「小时桶 0 个」——锁定空转也有日志。
- 用例 2（自愈）：初始化后连续两次自愈；第二次断言「开始」+「自愈完成：检查闭桶 …」+
  「补算 0 个」且 `检查闭桶 0 个` 不出现（确实扫到了桶、只是没有缺失）。
- **另加一条集成用例**（`tests/stats_snapshot_jobs_integration.rs`，超出原定「不做」范围）：
  用与 `init` 同一份 handler 工厂驱动 worker，断言失败 run 记 `failed` + 日志含「任务执行失败」与
  底层错误、正常执行记 `success`。两个场景合并在一个用例内顺序执行（任务锁是进程级的）。
- 只测外部可观察行为（日志文本、run 状态），不测内部计数结构。

## Out of Scope

- `usage_refresh` / `failure_recovery` 两个内置任务的日志与失败语义。
- 快照写入行数、各级水位等附加数据（用户否决）。
- 日志 i18n、前端 run 列表/日志弹窗改动。
- run 失败的重试/告警策略。

## Further Notes

- 空转断言依赖「运行期间不跨闭桶边界」：快照桶在终点 +60 分钟后才闭，测试毫秒级窗口内跨边界
  概率可忽略（既有用例同款假设）。
- 结束日志的桶数按 `META_WM` 顺序（小时/天/月/年）输出，与四级独立水位一一对应。
