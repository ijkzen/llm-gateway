# 供应商可用性状态机归一 — Spec

> 设计共识来自 2026-09-06 架构评审 grilling，完整决策记录见 `docs/adr/0003-availability-state-machine.md`；
> 领域术语见 `CONTEXT.md`「停用原因 (Disabled Reason)」「额度门控禁用」「连续失败禁用」。

## Problem Statement

供应商「能不能用」没有 owner：额度门控、连续失败禁用、管理员手动启停、恢复探测四处代码各自读写 `enable` 与 `failure_disabled` 两列，各自带着只有读代码才知道的附加规则（清失败计数器、级联停用/恢复虚拟模型条目、额度恢复不得解除失败禁用）。漏写任何一条就是线上 bug，且这些组合规则今天只能靠整条链路的集成测试撞见。

更具体的现存缺陷：库里分不清「额度耗尽停用」与「手动停用」（两者都是 `enable=false`）。管理员手动停用一个开了用量查询的供应商后，`usage_refresh` 只要在 5 分钟一轮的刷新里判定其额度充足，就会把它自动重新启用——管理员的决定被覆盖。

## Solution

把「供应商可用性」收敛为一个唯一的模块：所有改变供应商状态的代码（转发失败、额度刷新、管理员操作、恢复探测）都只通过该模块的动作入口改变状态，计数器清理、级联、守卫规则全部只写在这一处。同时把停用原因从布尔标志升级为四值字段（正常/连续失败禁用/额度耗尽/手动停用），使「额度刷新只恢复自己禁的供应商」成为可表达、可执行的规则——顺带修复上述缺陷。对管理员与网关调用方而言，启用/停用交互与 `/v1` 选路行为均不变。

## User Stories

1. As a 管理员, I want 手动停用供应商后它保持停用, so that 我的停用决定不会被额度定时刷新自动覆盖
2. As a 管理员, I want 手动启用一个额度仍耗尽的供应商后它被下轮刷新再次停用, so that 系统行为可预测、不会放行一个注定失败的通道
3. As a 管理员, I want 手动启用因连续失败被禁用的供应商立即生效并清零失败计数, so that 供应商不会刚启用就再次被连击误禁
4. As a 管理员, I want 启用/停用供应商时名下被级联停用的虚拟模型条目被正确恢复而手动关闭的成员不受影响, so that 级联不越权
5. As a 网关调用方, I want 供应商可用性判定口径与升级前完全一致, so that 我的请求选路不受架构重构影响
6. As a 开发者, I want 所有可用性迁移规则集中在一个模块里, so that 新增状态或修改守卫只改一处、不会出现「走了另一条入口就漏了」
7. As a 开发者, I want 禁用/启用组合矩阵能表驱动单测, so that 不必为验证状态组合启动 mock 上游服务器
8. As a 开发者, I want 失败计数器的「禁用不碰、恢复与手动启用必须清零」成为模块内规则, so that 计数器泄漏这类 bug 失去藏身处
9. As a 开发者, I want 数据库里的停用原因可直接区分四种状态, so that 排障时一条 SQL 就能回答「这供应商为什么是停的」
10. As a 开发者, I want 历史禁用行在升级后默认视为手动停用, so that 升级不会突然自动启用一批我来不及审查的供应商
11. As a 开发者, I want 恢复探测的乐观锁语义（探测期间状态被更新则放弃恢复）原样保留, so that 旧探测结果不覆盖新状态
12. As a 开发者, I want CONTEXT.md 的「停用原因」词条与代码状态一一对应, so that 人和 AI 讨论可用性时用同一套词

## Implementation Decisions

- 迁移 21：删除 `failure_disabled` 列，新增 `disabled_reason` 列，四值 `None`（正常）/ `failure`（连续失败禁用）/ `quota`（额度耗尽）/ `manual`（手动停用）。迁移编号沿用现行递增（当前最高 20）。
- `enable` 列保留作镜像，不变式「启用 ⇔ reason=None」由可用性模块统一写入保证；LB 选路与各查询过滤继续用 `enable`，前端契约零改动（`failure_disabled` 本就未暴露给前端）。
- 存量回填：`failure_disabled=1` → `failure`；`enable=false` 且非失败禁用 → `manual`（安全默认，宁多一次手动启用）；启用行 → `None`。
- 新建独立的可用性模块，动作式入口：`disable_for_quota` / `disable_for_failures` / `enable_manual` / `recover_probe`（探测的 `expected_updated_at` 乐观锁收进 `recover_probe`）；各动作自带幂等、级联（沿用现有 `cascade_disabled` 标记语义）与结构化日志。
- 失败连击计数器类型迁入该模块（应用状态中的字段随之换型），「禁用不碰计数器、恢复与手动启用必须清零」成为模块内规则；转发侧的「递增 + 阈值判断 + 停用 + 触发用量复查」收进单一 `record_failure` 形态动作，阈值由调用方传入，复查触发的异步派发留在转发侧。
- 额度刷新只对 `quota` 态自动恢复、对 `manual` 态完全不动；手动启用额度仍耗尽的供应商不设豁免，下轮刷新再次停用并标记 `quota`。
- 决策依据：ADR-0003（含被否决备选：保持两列三态、复用 `failure_disabled` 标手动、删 `enable` 单一事实源）。

## Testing Decisions

- 好测试只断言外部行为：库中 `enable`/`disabled_reason` 终态、虚拟模型条目级联结果、计数器值、返回的变更与否——不断言内部调用次序。
- 主缝 = 可用性模块动作入口：对内存 SQLite 表驱动验证禁用/启用组合矩阵（quota×manual×failure×正常 的停用与恢复交叉），先例为用量持久化模块的内存库测试。
- 迁移缝 = 合成旧结构库跑迁移 21，断言三类行的回填结果，先例为数据库模块的旧库迁移测试。
- 外层冒烟 = 既有三个集成测试文件（额度门控、失败恢复、LB 失败禁用）适配新列后原样保留，不为此重构改写结构。

## Out of Scope

- `provider.status` 死字段的清理（另行提案，未拍板）。
- `AppSettings` 设置包的类型化（架构评审候选 6，未纳入本轮）。
- LB 排序与剔除口径的任何行为变更（本次只收拢可用性规则，不动选路算法）。
- 前端展示停用原因（UI 不动；将来要做时数据已就绪）。
