# REQUIREMENTS: LB 熔断与失败复查（lb-circuit-breaker）

来源：用户原话（2026-09-03）——「为了提高服务质量，减少降级出现，现在对降级原因进行细化……订阅制缓存的用量信息过期，实际已无可用量，导致降级；失败后实时发出请求获取用量，如果确实不足，则直接禁用该供应商，连同供应商下面的所有模型一起禁用，依赖现存的 usage_refresh 定时任务来恢复启用状态；如果用量依然充足，但是请求就是失败……记一次连续失败次数，发生 5 次连续失败（可配置，从设置数据库中取，默认 5），则把该供应商连同模型一起禁用，usage_refresh 定时任务不要重新启用该供应商。按量付费按照同样的规格处理。」

## Scope

1. **连续失败计数**（内存，provider 粒度）
   - 转发链路中该供应商的成员请求失败即 +1：含 failover 循环 4 个失败分支（解密失败/构造失败/传输错误/可重试状态码）**与非可重试 4xx 终态路径**（用户拍板：所有失败都计）。
   - 该供应商任一请求成功即清零；进程重启清零（纯内存，仿 `LbState` 模式挂 AppState）。
   - 达到阈值触发「连续失败禁用」。

2. **失败复查**（异步后台，仅 `extra.usage=true` 的供应商）
   - 成员失败后后台触发实时用量抓取（`fetch_and_store` 强制刷新，结果写 DB 缓存）。
   - 同 provider 去重（已有进行中不重复触发）+ 节流（短时间内不重复真实抓取）。
   - 复查判定：额度/余额耗尽 → 走现有 `apply_usage_gate` 禁用供应商 + 级联停用子模型（usage_refresh 额度恢复后自动恢复）；充足 → 无动作（失败已由计数路径记录）。
   - 不支持用量查询的供应商跳过复查，仅计数。

3. **连续失败禁用**
   - 阈值 = 新设置项 `max_consecutive_failures`（Int 类型，默认 5，`app_settings.rs` 内存缓存、修改热生效）。
   - 动作：`enable=false` + 级联停用名下全部虚拟模型条目 + `failure_disabled=true`（**Migration 17**，provider 表新布尔列）+ warn 日志（request_id 关联）。

4. **usage_refresh 交互**
   - 仍照常刷新 `failure_disabled=true` 供应商的用量（前端展示）。
   - 恢复分支跳过 `failure_disabled=true` 的供应商——连续失败禁用不被自动恢复。

5. **手动恢复**
   - 管理员手动启用供应商：清除 `failure_disabled`、清零该 provider 计数；子模型仍只恢复 `cascade_disabled=true` 的条目（现有语义不变）。

## Non-goals（ponytail 裁剪与用户确认的非目标）

- 不做半开探测/自动恢复试探（连续失败禁用仅手动恢复）。
- 不做按模型粒度计数（provider 级）。
- 不改 4xx 不参与降级的现有行为（只是计数）。
- 不为失败计数引入持久化表（内存即可）。
- 不做通知/告警，禁用动作打日志即可。
- 节流不引入新依赖，用「in-flight 标记 + 上次抓取时间」的 Mutex 条目实现。

## Resolved questions（grilling 记录）

- 复查时机：异步后台（用户拍板），不阻塞降级链路。
- 适用范围：所有供应商统一计数与阈值禁用（用户拍板），查不到用量的无法复查但同样熔断、手动恢复。
- 失败口径：所有失败含 4xx（用户拍板，非推荐的仅可重试口径）。
- 计数存储：内存 + 成功清零（用户拍板）。
- 禁用表达：provider.failure_disabled 布尔（用户拍板，弃 disable_source 枚举）。
- 复查节流：去重 + 节流（用户拍板）。
