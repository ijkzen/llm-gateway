# SPEC: 连续失败供应商自动恢复

Label: `ready-for-agent` · Source: [REQUIREMENTS.md](./REQUIREMENTS.md) · 2026-09-03

## Problem Statement

供应商因连续失败达到阈值后会被标记为连续失败禁用，并从后续选路中移除。当前这种禁用只能由管理员手动解除，即使上游已经恢复、供应商仍有可用额度，它也会一直处于禁用状态，要求管理员持续人工巡检。

## Solution

增加一个每个整点运行的系统内置任务，只处理连续失败禁用的供应商。任务先利用已有用量能力排除明确无额度或无法确认额度的供应商，再对符合条件的供应商发送一次真实模型测试请求。测试成功后，任务解除连续失败禁用、恢复供应商参与选路，并同步恢复此前由供应商状态级联停用的虚拟模型条目；测试失败或任何前置条件不满足时保持现状。

## User Stories

1. As a 管理员, I want 连续失败禁用的供应商被定时复查, so that 上游恢复后不需要我逐个手动启用。
2. As a 网关调用方, I want 已恢复健康的供应商重新参与选路, so that 可用容量能够自动回到服务池。
3. As a 管理员, I want 恢复任务只扫描连续失败禁用的供应商, so that 手动禁用和额度门控禁用的供应商不会被误恢复。
4. As a 管理员, I want 恢复任务在每个整点执行, so that 复查节拍固定且容易理解。
5. As a 管理员, I want 支持用量查询的供应商先刷新用量, so that 不会为已耗尽额度的供应商产生无效模型请求。
6. As a 管理员, I want 只有明确仍有额度或余额时才进行探测, so that 用量抓取错误或数据不完整不会误触发恢复。
7. As a 管理员, I want 不支持用量查询的供应商仍能通过真实请求复查, so that 缺少用量接口不等于永久禁用。
8. As a 管理员, I want 每个供应商每轮最多发送一次探测请求, so that 自动恢复不会造成额外的上游请求风暴。
9. As a 管理员, I want 多模型供应商按稳定规则选择首个供应商模型, so that 探测行为可预测且可测试。
10. As a 管理员, I want 没有供应商模型的供应商保持禁用, so that 任务不会构造无效模型请求。
11. As a 管理员, I want 探测遵循供应商模型级、供应商级、直连的既有代理优先级, so that 自动探测与正常模型测试走相同网络路径。
12. As a 管理员, I want 只有上游 HTTP 2xx 才算探测成功, so that 传输失败、认证错误、限流和服务端错误都不会误恢复供应商。
13. As a 管理员, I want 自动探测写入现有请求记录, so that 我能审计恢复所依据的真实请求结果。
14. As a 管理员, I want 探测成功同时清除连续失败标记和失败计数, so that 已恢复供应商不会带着旧失败状态重新参与选路。
15. As a 管理员, I want 供应商恢复时只重开此前被级联停用的虚拟模型条目, so that 我手动停用的条目不会被自动任务覆盖。
16. As a 管理员, I want 探测失败不改变供应商或虚拟模型条目状态, so that 一次失败的健康确认不会产生状态抖动。
17. As a 管理员, I want 重复或重叠执行恢复任务保持幂等, so that 同一供应商不会被重复恢复或破坏状态。
18. As a 管理员, I want 探测期间发生的人工或其他状态变更得到尊重, so that 过期的探测结果不会恢复一个已不再属于连续失败禁用状态的供应商。

## Implementation Decisions

- 新增一个系统内置恢复任务，表达式固定为 `@hourly`，与现有系统任务一样在启动时幂等种入、注册处理器并由现有调度器加载；任务不新增运行时配置。
- 恢复任务只查询 `failure_disabled=true` 的供应商。`enable` 不是筛选来源，连续失败标记才是恢复资格的唯一依据。
- 支持用量查询沿用已有 `extra.usage=true` 判定。支持者每轮先强制真实抓取并持久化用量，不使用可能仍在有效期内的旧缓存。
- 用量判定复用既有订阅额度与按量余额三态谓词，并按供应商付费模式选择。只有 `Some(true)` 继续探测；额度或余额耗尽的 `Some(false)`、数据无法判定的 `None`、抓取失败均保持禁用并跳过探测。
- 不支持用量查询的供应商不经过用量前置条件，直接进入模型探测。
- 供应商模型按主键升序选择第一条。不存在供应商模型时不发送请求、不修改状态。
- 探测复用已有模型测试能力：同一最小请求、协议转换、凭证解密、模型级到供应商级的代理优先级、上游调用和请求指标落库逻辑。HTTP 2xx 成功，其余结果失败。
- 每个供应商每轮最多一次探测；任务各轮不为失败模型尝试其他模型。
- 自动探测沿用现有测试请求记录口径，不新增 schema 或专用统计字段。
- 恢复操作必须以数据库中该供应商仍为 `failure_disabled=true` 为条件进行原子状态转换，同时设置 `enable=true` 并清除 `failure_disabled`。条件不再满足时视为无需恢复，不覆盖当前状态。
- 供应商状态成功转换后，复用既有级联恢复能力，只启用带有级联停用标记的虚拟模型条目并清除其级联标记；手动禁用条目保持不变。
- 成功恢复后清零该供应商的进程内连续失败计数。探测失败、用量不允许探测或条件更新未生效时不重置计数。
- 任务应防止同一进程内的重叠整轮执行；单个供应商的错误记录日志后继续处理其他供应商，不能使整轮提前退出。
- 不增加新的数据库迁移、HTTP API 或前端功能。

## Testing Decisions

- 好的测试只断言外部可见行为：任务执行后的供应商启用状态、连续失败标记、虚拟模型条目状态、请求记录，以及系统任务是否正确种入和加载；不绑定内部函数拆分、锁结构或调用次数实现细节。
- 主 seam 是恢复任务的业务集成测试：使用真实测试数据库、本地 mock 用量接口与本地 mock 上游，直接执行一轮任务并检查最终数据库状态。
- 主 seam 覆盖：无用量能力且探测成功恢复；无用量能力且探测失败保持禁用；用量充足后探测成功恢复；用量耗尽、无法判定和抓取失败均不探测且保持禁用；无供应商模型保持禁用；多个模型只选择主键最小者；恢复只重开级联停用条目并保留手动禁用条目；成功与失败探测均产生现有测试请求记录；非连续失败禁用供应商不受影响。
- 并发/幂等行为通过重复执行和探测期间状态条件改变的集成场景验证，确保过期结果不覆盖当前状态。
- 调度接线 seam 沿用现有调度器测试方式：验证任务以 `@hourly` 幂等种入、注册处理器后可被加载，不通过等待真实整点验证时间行为。
- 既有模型测试请求、用量谓词和级联恢复已有各自测试，本功能不重复为其内部细节建测试套件。

## Out of Scope

- 前端页面、状态来源标签、开关和提示。
- 可配置执行间隔、指数退避、抖动、连续多次成功阈值或恢复通知。
- 每轮尝试多个模型、随机模型或按能力选择模型。
- 专用健康检查协议、专用 HTTP 端点、专用请求记录字段或状态历史表。
- 改变额度门控禁用、管理员手动禁用、正常转发失败计数或失败复查的现有规则。
- 自动恢复管理员手动禁用的虚拟模型条目。

## Further Notes

- 供应商模型自身没有启用字段；本需求中的“同步更新供应商模型状态”按现有领域模型落实为同步恢复该供应商下由级联动作停用的虚拟模型条目。
- 本功能有意修订旧的连续失败禁用规则：管理员手动启用仍可解除，新的自动恢复探测成功也可解除；普通用量刷新仍不能单独解除连续失败禁用。
- 该变化不需要数据库历史回填，因为恢复资格由已存在且已持久化的 `failure_disabled` 标记直接确定。
