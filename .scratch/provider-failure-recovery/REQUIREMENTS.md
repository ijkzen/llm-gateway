# REQUIREMENTS: 连续失败供应商自动恢复

来源：用户原话（2026-09-03）——「添加一个定时任务，每小时执行一次，用来重新启用因为连续失败而禁用的 provider，定时任务逻辑：找到哪些因为连续失败而被禁用的 provider，如果这个 provider 能够查询用量，先查询一次用量，如果用量还有剩余，发送一次请求，如果请求成功则恢复启用状态，否则保持禁用；如果没有用量，则依赖保持禁用；如果 provider 无法查询用量，则直接发送一次请求，根据请求是否成功修改 provider 状态；provider 状态发生变更要同步更新供应商模型状态。」

## Scope

1. 新增系统内置定时任务，每个整点执行一次，扫描 `failure_disabled=true` 的供应商。
2. 支持用量查询（`extra.usage=true`）的供应商先强制刷新一次用量：
   - 按现有订阅/按量可用性谓词判定；只有明确仍有剩余时继续探测。
   - 额度耗尽、余额耗尽、用量无法判定或抓取失败时保持禁用，不发送探测请求。
3. 不支持用量查询的供应商直接进入探测。
4. 探测按供应商模型主键稳定选择第一条供应商模型；没有供应商模型时保持禁用。
5. 探测复用现有模型测试请求语义：发送一次真实最小请求，沿用模型级→供应商级→直连的代理优先级，HTTP 2xx 视为成功，并写入现有 `request` 记录。
6. 探测成功时恢复供应商：`enable=true`、`failure_disabled=false`，并清零该供应商的内存连续失败计数。
7. 供应商恢复时同步恢复此前因供应商级联禁用的虚拟模型条目；管理员手动禁用的条目保持禁用。探测失败或任何前置条件不满足时不改变供应商及条目状态。
8. 任务重复运行、并发运行或状态已被其他路径修改时不得误恢复非连续失败禁用的供应商。

## Non-goals

- 不新增前端页面、开关或提示。
- 不新增恢复间隔配置、退避策略、连续多次成功阈值或通知机制。
- 不轮询全部供应商模型，不为单个供应商发送多次探测请求。
- 不新增专用探测端点、请求表字段、状态表或第三方依赖。
- 不改变额度门控禁用、管理员手动禁用和正常流量失败计数的既有语义。
- 不恢复管理员手动禁用的虚拟模型条目。

## Resolved questions

- 执行节拍：每个整点，采用 `@hourly`。
- 多模型选择：按供应商模型主键稳定取第一条，仅探测一次。
- 请求审计：沿用现有模型测试逻辑写入 `request` 表。
- 成功口径：上游 HTTP 2xx；传输错误、密钥错误和非 2xx 均失败。
- 用量口径：复用 `subscription_usable` / `balance_usable`；仅 `Some(true)` 放行，`Some(false)` 与 `None` 均保持禁用。
- 状态联动：供应商模型本身没有启用状态；用户所述同步更新落实为恢复该供应商下 `cascade_disabled=true` 的虚拟模型条目，不触碰手动禁用条目。
- 旧规则变更：连续失败禁用不再只能手动解除；管理员仍可手动恢复，自动恢复探测成功也可解除。
