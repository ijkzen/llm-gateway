# 订阅制窗口「截止日期优先」排序 — Spec

> 需求与决策记录见 `REQUIREMENTS.md`（同目录）。

## Problem Statement

虚拟模型订阅制优先策略（策略 0/1）的订阅组内排序，目前按 5小时→日→周→月窗口的剩余百分比逐层比较，仅同层精确打平才比该层重置时间。5小时窗口是滚动窗口，各供应商窗口截止时间不同：两个供应商在各自窗口内用了相近的额度（剩余百分比相近）时，排序由剩余百分比的细微差异决定，忽略了截止日期差异——即将到期的额度若不被优先消耗会被重置浪费。截止日期靠前的供应商应被优先消耗。

## Solution

订阅组内排序从「剩余百分比主导」改为「截止时间主导（FEFO，先过期先出）」：从最短窗口层（5h）起逐层检查，双方该层都有额度（窗口可用且剩余 > 0）时，跳过剩余百分比，改比**更上层**（期限更长的窗口）的截止时间链——截止时间更近者优先；一方有截止时间而另一方缺失时，有者优先；全部相同或缺失时，剩余百分比作最终兜底（沿用现有 5h→日→周→月 逐层比较）。双方某一层窗口不可用/无额度时该层判平，进入下一层。无用量数据的成员排在最后（现状不变）。

排序只影响同组内顺序；「可用性判定」（额度耗尽剔除/门控停用）口径不变。前端展示与运行时 LB 共用同一比较器，展示顺序自动同步。

## User Stories

1. As a 网关调用方, I want 两个订阅供应商的 5h 窗口都有额度时按更上层（周→月）的截止时间排序, so that 截止日期更近的供应商额度被优先消耗、避免到期被重置浪费
2. As a 网关调用方, I want 周截止时间相同的供应商再按月截止时间比较, so that 层级递进规则完整、排序可确定
3. As a 网关调用方, I want 截止时间链全部相同或全部缺失（厂商不返回 reset 时间）时退回剩余百分比比较, so that 排序永远有确定性结果、不依赖运气
4. As a 网关调用方, I want 一方该层窗口不可用（厂商不提供）时该层判平进入下一层, so that 不提供某窗口的供应商不会被误判更差（与现状一致）
5. As a 网关调用方, I want 同一层双方都有额度时才启用截止链比较、某方该层无额度（不可用/耗尽）则判平进下一层, so that 额度判定（>0）与排序语义清晰分离
6. As a 网关调用方, I want 某窗口缺失截止时间（resets_at）的供应商排在可判定者之后, so that 已知即将到期的额度不会被未知数据挤掉
7. As a 管理后台用户, I want 虚拟模型列表/编辑弹窗的成员展示顺序与真实 LB 顺序一致地反映截止日期优先, so that 我看到的就是请求实际会走的顺序
8. As a 开发者, I want 比较器纯函数单测覆盖全部新分支, so that 排序行为回归有据可查
9. As a 开发者, I want 真实 LB 链路有一个「截止日期优先」的集成测试, so that 比较器到选路的整条链路上行为正确
10. As a 开发者, I want 现有 48 场景测试与无截止时间的集成测试在新算法下保持绿, so that 剔除/分组逻辑不受排序语义调整影响
11. As a 管理后台用户, I want Command Code 供应商的月窗口展示重置时间, so that 月窗截止时间参与截止链排序、展示与真实一致

## Implementation Decisions

- **改动点**：只重写订阅制比较器（`usage_rank` 模块）内部实现，公开函数签名与调用方均不变。运行时 LB（`order_members` → `rank_by_quota_with`）与前端展示排序（`sort_items`）都路由到该比较器，自动同步，无需其他调用方改动。
- **Command Code 月窗截止时间补取**（用户补充需求，与排序算法配套）：Command Code 用量获取遗漏了月窗截止时间——`subscriptions` 接口实际返回 `currentPeriodEnd`（订阅周期结束 = 月度 credits 重置点），现有代码只取 `planId` 与 `currentPeriodStart`（后者仅用于 `usage/summary` 的 since），月窗 `resets_at` 被硬编码为 `None`。修复：subscriptions 解析增加 `currentPeriodEnd`，传入月窗窗口构造。
- **比较结构**（逐层）：层序 5h→日→周→月。
  1. 该层双方都「有额度」（窗口可用且剩余百分比 > 0；多窗口取最差剩余口径，与现状一致）→ 进入该层截止链：依次比较更上层（日→周→月）的截止时间。每层取该层窗口的 resets_at（最差剩余窗口口径）：
     - 双方都有 → 早者优先；
     - 一方有、一方缺失 → 有者优先；
     - 都缺失/窗口不可用 → 判平，继续往更上层。
  2. 截止链全平 → 剩余百分比兜底：按现有逻辑 5h→日→周→月 逐层比较剩余百分比（缺失判平、同层剩余打平比该层重置时间等行为全部保留）。
  3. 该层双方/某方无额度或窗口不可用 → 该层判平，进入下一层重做上述检查。
  4. 全部层判平 → Equal（调用方 shuffle 稳定排序实现随机兜底，现状不变）。
- **「有额度」判定**：剩余 > 0。运行时剩余 = 0 的成员在排序前已被「可用性剔除」过滤，不会到达比较器；比较器内的 >0 判定主要服务展示端（展示端不剔除耗尽成员）。
- **文档同步**：更新排序语义的代码注释与 AGENTS.md 描述（「剩余百分比 5h→周→月 逐层、同层打平比重置时间」→ 新算法），不改 `UsageData`/`QuotaWindow` 类型、不改 `subscription_usable`/额度门控、不改按量付费排序（`cmp_balance`）。
- **不改动**：前端零改动（共用比较器）；不新增配置项；不做综合分/时间衰减等复杂模型。

## Testing Decisions

- **测试原则**：只测比较器的外部可观察行为（给定两组窗口数据 → 排序结果），不测内部实现细节。
- **比较器单测（主战场，最高缝）**：`usage_rank` 模块内重写/新增用例，覆盖：
  - 5h 都有额度 → 周截止更近者优先（即使 5h 剩余百分比更低）；
  - 周截止相同 → 月截止更近者优先；
  - 截止链全平/全缺失 → 兜底按剩余百分比决胜；
  - 某方 5h 窗口不可用 → 判平进周层、周截止决胜；
  - 某方截止时间缺失 → 排在可判定者之后；
  - 多窗口取最差剩余口径在额度判定与兜底中保持生效；
  - 无数据成员排最后（现状回归）。
  用例风格沿用现有表驱动/直接断言排序结果的写法。
- **集成链路测试**：`proxy_integration.rs` 新增 1 个真实 LB 测试（沿用现有 mock 上游 + 预置用量缓存的模式）：订阅成员 A 5h 剩余高但周截止远、B 5h 剩余低但周截止近 → 策略 0 转发应命中 B（截止日期优先在真实链路上生效）。现有 `subscription_first_ranks_by_remaining_five_hour_usage`（数据无截止时间 → 走兜底路径）断言不变。
- **场景回归**：`lb_48_scenarios.rs` 48 场景测试数据无 resets_at → 走兜底路径，断言与期望链不变；仅文件头注释补一句「订阅数据无截止时间，走剩余百分比兜底路径」避免后人误解排序假设。

## Out of Scope

- 按量付费（balance）排序：无截止时间概念，不受影响。
- 额度耗尽判定/门控（`subscription_usable`、`apply_usage_gate`、用量刷新）语义调整。
- 前端任何代码改动。
- 5h 层自身截止时间参与排序（用户明确跳过：5h 窗口每 5 小时滚动，截止时间在 0-5h 内密集分布，直接比较会主导排序且近似随机）。
- 日层是否提供的展示/口径变化。

## Further Notes

- 用户原始诉求强调「截止日期靠前的供应商额度应被优先消耗」，本质是避免「额度到期被重置而浪费」——FEFO 策略。周/月窗口同样适用（订阅周期不同步时，快重置的一方先消耗）。
- 现实数据中周/月 resets_at 缺失并不少见（部分厂商不返回 reset 时间、月窗占位时间戳被过滤），因此「截止链全平 → 剩余百分比兜底」不是理论分支而是日常路径，测试必须覆盖。
