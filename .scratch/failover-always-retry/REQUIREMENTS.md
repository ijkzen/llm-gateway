# REQUIREMENTS — 降级策略：任何成员失败都降级重试

## 请求原文

> 降级策略不再使用状态码的白名单机制，而是只要请求失败，就进行降级重试。

## 背景（生产事故驱动）

2026-09-08 17:36 生产诊断（request_id `d9151f98-83a9-46a5-b0fc-ef5c0592b066`）：
虚拟模型 deepseek-v4-flash（vm=1）的 LB 首选成员 provider 4（Command Code 订阅通道）上游
返回 **HTTP 400 insufficient credits**。400 不在原可重试白名单（408/429/500/502/503/529）内，
网关直接把上游错误透传给客户端——尽管降级策略开启（fallback_strategy=1）且后面还有
3 个候选成员（5/26/19）。用户手动停用 provider 4 后同一请求走 provider 5 即成功，
证明「换成员本可成功」。

根因：上游额度判定与网关用量缓存脱节（缓存 weekly 剩 0.34% > 0，未触发额度剔除/门控），
且「额度耗尽」类错误以 400 返回时被一刀切归入不可降级。

## 决策（已拍板）

1. **删除 HTTP 状态码白名单**：`FailureStage::Http` 不再查 `is_retryable_status`，
   任何失败（本地失败或上游 >=400）在降级策略开启且还有后继成员时一律降级尝试下一成员。
2. **全部统一生效**：chat/completions 与原生透传（/v1/messages、/v1/responses）共用
   `forward_through_members` 循环，改动一处、两端生效（不按 flavor 区分规则）。
3. **失败边界 = >=400**：3xx 仍按成功路径处理（现状不变，不扩范围）。
4. **终态错误 = 最后尝试成员**：全部成员都失败时，客户端收到最后一个尝试成员的状态码
   与错误消息（保留现有 last_failure 逻辑）。
5. **实现方式 = 删死抽象**：`FailureStage` 枚举、`is_retryable_status()`、`retryable()`
   方法及其 3 个单测一并删除，4 处失败分支直接判 `retry_enabled && has_more`。
6. **日志文案**：Http 失败降级 warn 日志去「可重试」三字（
   「上游成员返回可重试错误」→「上游成员返回错误」）。

## 不变项（显式排除）

- `fallback_strategy = 0`（失败直接返回）行为不变；开关仍是总闸。
- 失败计数/熔断（`note_member_failure`/`availability::on_forward_failure`）不变——
  现状即对所有失败计数（含 4xx），任一供应商失败达 `max_consecutive_failures` 即禁用。
- 降级失败落库行（request_id 带 `-N` 后缀）机制不变。
- 同一请求内同供应商多成员失败只计一次（counted_failures 集合）不变。
- 无退避延迟：降级立即尝试下一成员（现状如此）。
- 流式响应开始后（200 + SSE 已向客户端输出）的中途失败不降级（技术边界：数据已不可回退）。
- 用量感知剔除/额度门控（`usage_rank`/`apply_usage_gate`）不动——本次只改失败后行为，
  不扩到「用量数据与上游口径对齐」这一独立问题。
- 不新增任何配置项/设置。

## 非目标

- 不改 Command Code/上游用量口径（额度数据与上游判定脱节是独立问题，见背景）。
- 不为「额度耗尽」类错误单独识别降级——全量降级已覆盖该场景。
