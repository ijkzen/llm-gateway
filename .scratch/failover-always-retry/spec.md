# SPEC — 降级策略：任何成员失败都降级重试

> 来源：`.scratch/failover-always-retry/REQUIREMENTS.md`（Stage 1 细化，6 决策 + 2 裁剪全经用户拍板）

## Problem Statement

生产事故（2026-09-08，request_id `d9151f98-83a9-46a5-b0fc-ef5c0592b066`）：
虚拟模型首选成员上游返回 **HTTP 400 insufficient credits**（额度实际已耗尽，与网关用量缓存
显示不一致）。网关的降级（failover）策略只对状态码白名单（408/429/500/502/503/529）
生效，400 被当作「客户端请求错误」直接透传终态——尽管降级策略开启、虚拟模型还有多个
可用候选成员（换成员实测成功）。用户视角：一次「上游没钱了」的失败，网关没有尝试任何
其他成员就整体失败。

## Solution

虚拟模型降级策略不再按 HTTP 状态码区分可降级与不可降级：只要对某个成员的转发失败
（本地失败：解密/构造/传输，或上游返回 >=400），在降级策略开启（fallback_strategy=1）
且还有后继成员时，一律降级尝试下一成员，直到成功或全部成员尝试完毕；全部失败时返回
最后一个尝试成员的错误。chat/completions 与原生透传（/v1/messages、/v1/responses）
统一生效。

## User Stories

1. 作为 llm-gateway 使用者，当我的虚拟模型首选成员上游返回 400（如额度耗尽 insufficient
   credits、模型名不匹配、鉴权失败等任何 4xx），我希望网关自动尝试下一个候选成员，
   以便请求在成员可用时仍能成功，而不是整体失败。
2. 作为 llm-gateway 使用者，当虚拟模型全部成员都失败时，我希望收到最后一个尝试成员的
   状态码与错误消息，以便了解最终失败的真实原因。
3. 作为 llm-gateway 使用者，当我的虚拟模型降级策略关闭（fallback_strategy=0）时，
   我希望失败行为保持现状（直接返回错误、不尝试其他成员），以便保留「快速失败」选项。
4. 作为管理后台使用者，我希望看到每次降级尝试在请求记录中单独留痕（request_id 带 -N
   后缀、success=false、fail_reason 记该成员失败原因），以便排障时能看到完整尝试链。
5. 作为运营者，我希望供应商的连续失败熔断/自动停用机制不受影响（4xx 失败同样计数，
   达阈值禁用），以便故障供应商仍能被自动摘除。
6. 作为 /v1/messages、/v1/responses 原生透传的使用者，我希望降级行为与 chat/completions
   一致（任何失败都尝试下一成员），以便原生端点同样受益于成员冗余。

## Implementation Decisions

- **判定退化**：成员尝试循环中「是否降级」的判定从「按失败分类查白名单」退化为
  `降级策略开启 && 还有后继成员` 两个布尔条件；删除失败分类枚举与状态白名单谓词
  函数（判定语义统一后成为死抽象），4 处失败分支（解密/构造/调用/上游 >=400）
  直接使用该判定。
- **失败边界**：上游 >=400 即失败；3xx 仍按成功路径处理（现状不变）。
- **终态选择**：保留现有「最后失败快照」逻辑——循环结束返回最后一个尝试成员的
  状态码与错误消息（本地失败类固定 502 的现状不变）。
- **范围**：改动点在 chat 与原生透传共用的成员尝试循环内，两入口自动统一生效；
  不按端点类型区分规则。管理后台聊天直连（无成员循环/无 failover 的独立路径）不受影响。
- **日志文案**：上游 HTTP 失败降级日志去掉「可重试」措辞（如「上游成员返回错误，
  降级重试下一成员」）。
- **不变项**：fallback_strategy=0 语义、失败计数与熔断（所有失败均计数、同一请求内
  同供应商只计一次）、降级失败落库行（-N 后缀）、无退避立即降级、流式开始后的中途
  失败不降级（技术边界）、用量感知剔除/额度门控逻辑。
- **不新增**：无新配置项、无设置项、无 schema 变更、无 API 契约变化、无前端改动。
- **文档**：AGENTS.md 中「failover 重试（408/429/500/502/503/529）」描述同步为全量
  降级语义（docs: 单独提交）。CONTEXT.md/ADR-0020 词条与改动兼容，无需修改。

## Testing Decisions

- **测试缝**：集成测试层（全链路：HTTP 入口 → 成员尝试循环 → request 落库）。
  这是锁外部行为的最高 seam，仿照现有 429 降级用例结构。
- **新增用例**：mock 成员 A 上游返回 400（OpenAI 错误体），成员 B 正常成功；
  断言（a）最终 HTTP 200 且由成员 B 服务；（b）落库含成员 A 的降级失败行
  （-1 后缀、success=false、fail_reason 含上游错误消息）与成员 B 的成功行。
- **删除用例**：随死抽象删除的 3 个单元测试（本地失败判定矩阵 / HTTP 白名单矩阵 /
  策略与成员约束）——判定退化为平凡布尔逻辑后无单元层替代价值，行为由集成测试锁定。
- **不改动**：既有 429 降级、全部成员失败、fallback=0 直接失败等集成用例（行为不变）。
- **好测试标准**：只断言外部可观察行为（响应成员、落库行、后缀），不测实现细节。

## Out of Scope

- 上游额度口径与网关用量缓存脱节的问题（usage fetcher/额度门控的独立课题）。
- 为「额度耗尽」类错误做消息级识别（全量降级已覆盖）。
- ADR-0020「每次失败后按同策略重选」措辞与代码（固定顺序遍历）的既有漂移修正。
- 流式中途失败（已向客户端输出数据后）的降级。
- 前端展示、API 契约、配置项。

## Further Notes

- 本改动使「上游业务 4xx」也消耗一次成员尝试；无退避、串行尝试，最坏情况延迟 =
  全部成员各一次失败往返之和。用户已接受该权衡（对比：此前 4xx 一失败即返回）。
- 集成测试中 400 错误体需用真实上游形态（`{"error":{"message":...}}`）以覆盖
  `extract_error_message` 路径。
