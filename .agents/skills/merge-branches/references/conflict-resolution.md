# 冲突解决深入细则

本文件是 SKILL.md「冲突解决」章节的展开参考。遇到冲突且 SKILL.md 的速查表不足以定夺时，按这里的流程执行。

## 1. 先看冲突的全貌

```bash
git status                      # 冲突文件清单与两侧状态（UU/AA/DD/AU/UA）
git diff                        # 未解决冲突的 diff（带冲突标记）
git diff --name-only --diff-filter=U   # 只看未合并文件
```

每个冲突标记块的语义：

```
<<<<<<< HEAD          ← main 当前内容（已合入侧）
...A...
=======
...B...               ← 待合分支内容
>>>>>>> <分支名>
```

## 2. 判定冲突类型，选对策

| 类型 | 特征 | 对策 |
| --- | --- | --- |
| **同文件不同位置各加代码** | 冲突块互相独立 | 两侧都保留（git 通常能自动合，手合时按区块拼） |
| **同一逻辑两侧都改** | 冲突块重叠 | 看哪侧是"新语义"，或两者互补；结合规格定 |
| **一边删一边改** | 一侧删除某段，另一侧改了该段 | 通常保留"改"的一侧（删除常在重构侧，需判断） |
| **签名/接口变更** | 一侧改定义，一侧改调用 | 保新定义 + 适配调用方，语义两端都要对 |
| **重命名/移动** | 一侧移动文件，一侧改内容 | 用 `git log` 追文件历史确认双方意图 |
| **测试文件双方各加用例** | 不同 describe/test 块 | 按块重组保留双方用例；git ort 自动合可能产出缺 import/缺 helper 的"语义错配"，要跑测试兜底 |
| **i18n key** | 双方各加 key | 都保留；**en/zh-CN 必须成对**，缺翻译会让界面出现英文 key |

## 3. 规格驱动决策（本仓库的硬规则）

本仓库的正式需求/规格在 `.scratch/<feature-slug>/`，典型结构：

```text
.scratch/<slug>/
├── REQUIREMENTS.md          # 需求（用户语言，讲清要什么）
├── SPEC.md                  # 规格（实现口径、行为定义、接口契约）
└── issues/
    ├── 01-xxx.md            # 任务拆分（NN- 前缀，按序执行）
    ├── 02-xxx.md
    └── ...
```

查找方法：

1. `ls .scratch/` 列出全部 slug。
2. 按分支名推断：`feat/api-key-race-nav` → `.scratch/api-key-race-nav/`；`fix/virtual-model-item-detail` → `.scratch/virtual-model-item-detail/`；`feat/overview-today-stats` → `.scratch/overview-today-stats/`。slug 可能与分支名不完全一致（如分支名带 `fix/` 前缀），在 `.scratch/` 下按语义找。
3. 冲突解决时逐条对照 SPEC 中相关行为定义（统计口径、字段、状态、排序规则等），**合并产物不得与 SPEC 相悖**。

**决策层级**：两侧内容能互补共存 → 直接互补合；语义相悖无法共存 → 以 SPEC 为准；SPEC 没有覆盖或 SPEC 互相矛盾 → 问用户（见下）。

## 4. 什么时候必须问用户（AskUserQuestion）

以下情况**不要猜、不要自行发明**，用 AskUserQuestion 把问题讲清楚：

- 冲突两侧表达的是**互斥的行为选择**，且无规格或规格没覆盖。
- 两个分支的规格文件（或代码体现的口径）**互相矛盾**。
- 冲突涉及**生产数据语义/历史数据口径**（如状态位、统计窗口、迁移），猜错会污染存量数据。
- 合并结果会**改变已拍板的用户可见行为**（UI 文案之外）。

提问模板（中文，讲人话）：

> 合并 `A分支` 与 `B分支` 到 main 时，`<文件>` 第 N 行附近发生冲突：
> - main/`A分支` 侧：<该侧做了什么，一句话+涉及的行为/规格>
> - `B分支` 侧：<该侧做了什么，一句话>
> 两处改动都会影响 `<某个行为>`，但处理方式冲突（<具体怎么冲突>）。
> `.scratch/<slug>/` 下没有能定夺的规格说明（或：两份规格对 <X> 的描述不一致：A 说…、B 说…）。
> 应该保留哪一侧 / 怎么合并？

给出可操作的选项（保留 A / 保留 B / 按某方式融合），不要问"你觉得呢"这种开放式问题。用 preview 字段贴关键冲突代码帮用户快速判断。

## 5. 解决后的验证

- 冲突文件全部 `git add` 后 `git commit`（保留 merge 预填信息）完成合并。
- **验证先行**：跑针对性测试确认合并产物行为正确：
  - 后端：`cargo test --all-targets`（或先 `cargo test <相关模块>` 快速验证，最终仍要全量）。
  - 前端：`pnpm vitest run` 相关测试文件，如 `pnpm vitest run src/__tests__/overview-page.test.tsx`。
- 语义可疑处（尤其统计/排序/门控类）结合 SPEC 人工核对一遍合并结果。
