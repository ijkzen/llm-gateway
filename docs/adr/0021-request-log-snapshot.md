# 0021 — 统计快照预聚合（request_log_snapshot）

## Status

accepted

## Context

`request` 表历史行写后即不变（落库即终态，ADR-0014 口径），但数据面板 12 个统计端点（summary/charts/insight/5×rank/4×metrics）每次查询都实时全扫聚合同一批历史数据——随库增长查询越来越重且纯属重复劳动。历史数据「会变」的唯一窗口是请求完成前（异步落库，写完不再变），因此按时间桶把闭口数据预聚合落库、查询只实时算增量，在语义上无损。

## Decision

1. **快照表为窄表（EAV）**：`request_log_snapshot` 一行 =（时间桶）×（主体）×（指标名）×（值）。指标以加和/计数原语存储（跨桶加总后现算比率/均值，口径与实时 SQL 一致），延迟分位数（p50/p90/p95/p99）在闭桶时对该桶原始值**精确**计算后作为标量行存储——不采用直方图近似（用户否决）。
2. **时间桶四级独立物化**：hour/day/month/year 各自直算 request 表（不从细粒度行滚粗），每级独立哨兵行与自愈（用户否决「月/年读时归并」）。桶边界按设置表时区对齐（ADR-0015 单一来源）。
3. **主体列用类型+键**：entity_type ∈ {whole, provider, model(provider_model.id), virtual_model, api_key(id)}，主体键一律用对应表主键 id（含 api_key——request 行存名称，生成时按唯一名映射）；跨维组合由主体交叉相乘派生新类型（如虚拟模型成员 = virtual_model × provider_model），entity 值用英文逗号连接复合键（用户定义）。
4. **固化余量 60 分钟**：桶终点 + 60 分钟后的桶才固化（生成/读取均按此判定），图表对最近 1~2 个桶保持实时读；持续超过 60 分钟的流式请求行（跨过固化时刻才落库）会从该小时桶快照漏记，但日/周/月级视图由更粗粒度桶行覆盖、实时查询口径不受影响。
5. **实时兑底是第一类规则**（用户强调）：快照未生成或未覆盖的部分（未闭桶、缺哨兵行、时区/边界不匹配）一律实时聚合 request 表，快照只是加速层，绝不因缺快照返回错误或空数据。闭桶即使零流量也写 whole 全 0 哨兵行，「哨兵存在」=「该桶已固化」，兼作自愈缺口检测依据。
6. **内置任务两个**：`stats_snapshot`（@every 1h）幂等 upsert 自上次以来新闭口的四级桶（首启表空时整体全量回填整个历史，幂等无断点）；`stats_snapshot_rebuild`（@every 1h）自愈扫描最近 7 天闭口小时/天桶 + 最近闭月/闭年点检补缺口。meta 记录生成所用时区，设置表时区变更自动触发全量重算（用户否决手动方案）。
7. 失败原因分布不进快照（EAV 结构无原因维度列），insight 该组兑底实时；接口 JSON 形状与数字口径不变。

## Consequences

- 查询成本与窗口长度解耦：任意窗口 ≈ 快照行数（桶数×主体数）+ 恒定的小实时尾部（≤ 固化余量内增量），历史越长收益越大。
- 正确性由「读路径实时兑底 + 闭桶判定」双保证：任何缺快照场景退化为实时查询而非错误数据。
- 迁移 26 起编（生产 14/15 号段废弃），快照行与 request 行同样不设保留期清理。
- 时区/设置变更影响快照桶对齐时，代价是回到实时兜底直至全量重算完成，功能不中断。

规格：`.scratch/request-log-snapshot/`。
