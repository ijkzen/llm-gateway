# 我放着现成的 LLM 网关不用，愣是让 Kimi Code 陪我从零写了一个

> 一个网关而已，开源的一大把，你干嘛非要自己写？
> 这话我听得耳朵起茧了。今天就把话说明白：因为现成的那些，我用着是真难受。

---

## 开头：One API、New API 我都用过，然后全卸了

市面上不是没有现成的网关。One API、New API 都开源多少年了，用的人一堆。我全试过，
然后一个个卸载了。不是它们不好，是它们**不适合我这种个人用户**。

**第一个劝退我的：功能是真多，噪音也是真大。** 我就想管好我自己那几把 API Key，
结果一打开界面，扑面而来的是令牌分组、渠道分组、充值、兑换码、邀请返利……这都啥跟啥？
我又不是开站的站长，这些东西对我来说不是功能，是纯纯的干扰。

**第二个：内存占得我心慌。** 就拿 New API 来说，常态跑起来要 100MB 左右。
挂在我服务器上，总觉得哪哪不得劲。一个转发网关，至于这么重吗？

**第三个，也是最关键的：它们根本看不到「用量」。** 我同时订了好几家 Provider——
OpenCode Go、Kimi、智谱、MiniMax、火山……每家都是订阅制，都有 5 小时/周/月的窗口，
额度剩多少、啥时候重置，全都散落在各家后台，我想集中看一眼都没门。
One API 和 New API 就是纯转发，压根没有「帮你查各家用量」这个功能。

需求其实挺朴素：一个轻量的、干净的、能看用量、能自动负载均衡和降级的自托管网关。
现成的满足不了，那就自己写呗。**这就是 llm-gateway 的由来——一个跑起来只要十几 MB、
能聚合多家供应商、能自动查用量还带额度门控的小东西。**

整个开发过程，我几乎全程都丢给 Kimi Code 了。这篇想聊的，不是「这网关多牛」，
而是**一个想法，是怎么在 Kimi Code 的陪伴下，一步步变成能开源的真东西的**。

---

## 第一步：别急着写代码，先让 Kimi Code 给我指条道

很多人让 AI 写东西，上来就是「帮我写个 XX」。我的习惯正好反过来——
**先问它：这事儿该咋干？**

我把它当成一个经验丰富的架构师来请教：我想做个 LLM 网关，你觉得整个流程应该怎么走？
它没甩代码，先给我画了一条路：

> 先调研——网关的核心是格式转换，你得先搞明白各家协议怎么互转，该参考哪些项目；
> 再分批实现——按模块拆，先做供应商管理，再做转发，再做用量；
> 每一批都要有测试，规格先行。

这条路后来我完整走了一遍。回头看，**它最值钱的地方不是「给了标准答案」，
而是让我动手前心里就有张地图**——我知道自己在哪、下一步往哪走，而不是走一步看一步。

---

## 第二步：调研，不是瞎翻，是精准对标

「调研」听着虚，但在网关这行非常具体：**你想做的每件事，都有现成的参考能抄。**
Kimi Code 帮我干的第一件实事，就是把这些参考项目一个个挖出来。

- **格式转换参考谁？** 网关得把 OpenAI 兼容 / OpenAI Responses / Anthropic / Gemini
  四套协议互转。它调研完告诉我：LiteLLM 是这行的标杆，协议转换层被无数项目验证过，
  值得一段段对着学。
- **用量查询参考谁？** 我要查 8+ 家供应商的订阅用量，每家接口都不一样（有 API Key 直查的、
  有要 AK/SK 签名的、有得解密 CookieCloud 的）。它又挖出两个宝贝：**CC Switch** 和
  **CodexBar**——这俩开源项目把各家用量接口都逆向过了，简直就是现成的「答案书」。

于是整个实现就有了地基：协议转换对着 LiteLLM 写，用量 fetcher 对着 CC Switch / CodexBar 写。
不是闭门造车，是踩着前人的肩膀爬——这恰恰是 Kimi Code 帮我省下的最大一笔时间。

---

## 第三步：规格驱动 + 测试驱动，一批一批来

调研完，开干。这一步它干活的方式让我印象特别深——**不是想到哪写到哪，
是规格驱动（spec-driven）+ 测试驱动（test-driven）。**

每个模块先写一份规格说明（这功能要干啥、边界在哪、术语怎么定），再写测试把关键行为
钉死，最后才写实现。听着麻烦，好处巨大：**功能稳定、基本没 bug。**

- **供应商管理**：规格里写死「供应商 = base_url + api_key（加密存）+ 协议类型」，
  API Key 用 AES-256-GCM 加密。
- **模型目录智能填充**：从 models.dev 内嵌 363 条模型元数据，按「尾段匹配」自动补全模型详情。
- **虚拟模型聚合**：多供应商模型聚成一个 `display_id`，4 种负载均衡策略 + failover 降级。
- **四协议转发**：对着 LiteLLM 一个个协议实现，请求+响应+流式+usage 归一化，每个协议配转换测试。
- **用量 fetcher**：对着 CC Switch / CodexBar 一家家实现，归一成订阅窗口（5h/周/月）或余额。
- **用量门控**：每 5 分钟定时刷新，额度耗尽的供应商自动停用、恢复自动启用。

一批一批来，每批都有规格有测试。到后期，项目攒了 **210+ 单元测试 + 16 个集成测试文件**。
这些测试不是摆着好看的——它们是「敢随手重构」的底气。

## 第四步：那些具体的坑，才是真实的部分

前面说得有点顺，其实过程里全是坑。举两个例子，都是 Kimi Code 陪我趟过去的。

**坑一：OpenCode Go 的用量接口，到底用哪个请求头？**

查 OpenCode Go 的用量，它一开始按常规思路用 `x-api-key` 头去请求
`opencode.ai/zen/go/v1/usage`，结果 `401 AuthError` 弹了回来。折腾半天才发现：
**这接口只认 `Authorization: Bearer`，跟推理侧 `/messages` 用的 `x-api-key` 正好相反！**
而且 `401` 和 `403` 的意思也完全不一样——`401` 是 key 没带对，`403` 是 key 没问题但没买 Go 订阅。
这种坑，光看文档根本发现不了，非得实测。

**坑二：TTFT / TPS 的统计口径，改了三四次**

网关要记每次转发的指标：首字延迟（TTFT）、吞吐（TPS）。这个统计口径我们前前后后
改了三四次：一开始 `network_latency` 单独记，后来并进 ttft；TTFT 起点从「请求发出」
挪到「上游建连完成」；流式推理还得单独补 ttft；连接池复用之后，指标语义又得区分……

改口径最怕啥？**牵一发动全身**——流式/非流式两条路径、相关测试、前端图表全要一起动。
它那个「改→跑测试→看失败→修」的循环，加上它能记住前面所有约定，让这种反复打磨
没变成一场灾难。我只需要在关键节点瞄一眼，说「不对，这儿应该这样」，它就能顺着改下去。

说这俩例子，是想说明：**开发根本不是「AI 一行行敲代码」那么浪漫，而是大量的试错、
修正、打磨——而 Kimi Code 把这些脏活累活全接过去了。**

## 第五步：跑通之后，是漫长的「抠细节」

功能基本跑通后，进入最磨人的「完善期」。这阶段它还在，但角色变了——
从「写功能」变成「抠细节」。

- 列表默认选中首个、选中态圆角、表格空态去白底、侧边栏调整……
- 请求日志页面从零做起：服务端分页、过滤、详情弹窗、供应商名称按 providerId 查……
- 给网关换了个有语义的 favicon，把 logo 图标也换了……
- 图标、主题、空态、交互细节……

这些提交看着琐碎，但正是它们把「能用的项目」变成「愿意用的项目」。
而且因为它手里攥着整个上下文，改 UI 不会弄坏后端，改后端不会忘了前端——
这种「整体感」，是我觉得它最金贵的地方。

## 第六步：连开源，都是它调研出来的流程

功能磨得差不多了，我开始琢磨开源。这又是一次「先调研」——只不过这次调研的是
**「怎么把一个项目正经准备成开源项目」**。

它给我列了一份开源清单，我们一项项做掉：

- 重写 README，面向开源用户而不是自己
- 补 MIT LICENSE、CONTRIBUTING、SECURITY、行为准则、issue/PR 模板
- **Dockerfile 去私有化**：原来构建依赖内部 Harbor 镜像，改成全公网可构建（多阶段 + cargo-chef + rustls 纯 Rust TLS）
- 加 GitHub Actions：CI（测试/clippy/fmt）+ Docker（构建推送 GHCR）
- 根目录放 `compose.yaml` 示例，让人 `docker compose up -d` 就能跑
- 把内部 Gitea CI、内部镜像地址这些「私货」从公开仓库清干净

于是 `github.com/ijkzen/llm-gateway` 正式开源，镜像在 `ghcr.io/ijkzen/llm-gateway`。
**开源不是「把代码传上去」就完事，它是一整套工作流——而 Kimi Code 把这也包圆了。**

## 最终产出

- **llm-gateway**：Rust 2024 + Axum 0.8 + SeaORM/SQLite（WAL）+ React 19 + Vite + shadcn/ui
- **轻量**：跑起来内存约十几 MB，是 New API（约 100MB）的 1/8
- **工程质量**：210+ 单元测试 + 16 个集成测试文件 + 27 个前端测试文件（109 用例）
- **已开源**：`github.com/ijkzen/llm-gateway`（MIT），Docker `ghcr.io/ijkzen/llm-gateway`
- **一个入口管所有**：客户端只认 `/v1/chat/completions` + 一把 `lg-` API Key
- **用量透明**：8+ 家厂商额度/余额集中展示，耗尽自动停用、恢复自动启用
- **可靠降级**：上游 5xx/429 自动 failover 到虚拟模型内其他成员

## 经验总结

回头看这整个项目，Kimi Code 帮到我的，不是「替我敲了多少行代码」，而是这几件更实在的事：

1. **先给流程，再写代码。** 它让我动手前就有全局地图：先调研、再分批实现、规格先行、
   测试兜底。这流程本身，比任何一行代码都值钱。

2. **精准调研，踩着前人肩膀。** 协议转换参考 LiteLLM，用量查询参考 CC Switch / CodexBar——
   这些参考项目是它挖出来的，让我没闭门造车。

3. **规格 + 测试，换来「敢改」的底气。** 210+ 测试不是负担，是持续重构的安全网。
   没有它，指标口径改三四次这种事，我根本不敢碰。

4. **长上下文 = 整体感。** 它记得项目所有约定，改 UI 不弄坏后端、改后端不忘前端、
   磨指标不丢之前的决策。这是「一个人撑起大项目」的秘密。

5. **连开源都是它的调研结果。** 从 README 到 LICENSE 到 CI 到 compose，一套流程走完，
   项目才真正「属于社区」了。

最后说一句：这篇文章写的是 llm-gateway，但它更像一个样本——**一个想法，怎么在 AI 的
陪伴下，从调研、到实现、到打磨、到开源，完整走完一遍**。你要是也在纠结「要不要自己造轮子」，
希望这个样本能给你点参考。
